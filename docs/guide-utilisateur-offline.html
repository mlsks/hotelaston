Faire tourner le site sur le PC, et travailler avec GitHub

Pas à pas pour Windows : lancer le serveur, voir le site sur le portable, récupérer les mises à jour, relire et fusionner une pull request, pousser ses propres modifications, mettre à jour la démo Render. Cette page marche sans internet : un double-clic sur le fichier suffit.

L'essentiel

Le projet est sur le PC foupax2, dans le dossier C:\Dev\Claude\Remotion\hotelaston. Le code est aussi sur GitHub, dans le dépôt mlsks/hotelaston. Quatre situations reviennent tout le temps :

Voir le site

  2. npm start
  3. Ouvrir 127.0.0.1:3020/admin/
Détails

  1. La relire sur github.com
  2. Merge pull request

À retenir. Les textes, traductions, photos et réglages modifiés dans l'admin sont dans la base locale du PC, pas sur GitHub. Ils ne passent donc jamais par git : il suffit de cliquer sur Publier. GitHub ne contient que le code et la documentation. Voir Où est quoi.

1. Ouvrir le terminal au bon endroit

Toutes les commandes de ce guide se tapent dans PowerShell (ou « Terminal », c'est la même chose sous Windows 11). Le plus simple pour l'ouvrir directement dans le bon dossier :

  1. Ouvrir l'Explorateur de fichiers (Windows + E) et aller dans C:\Dev\Claude\Remotion\hotelaston.
  2. Cliquer dans la barre d'adresse en haut (là où le chemin est écrit), effacer le chemin, taper powershell et appuyer sur Entrée.
  3. Une fenêtre bleue ou noire s'ouvre. La ligne se termine par PS C:\Dev\Claude\Remotion\hotelaston> : on est au bon endroit.

Autre méthode : clic droit sur le bouton Démarrer, Terminal, puis taper :

PowerShell
cd C:\Dev\Claude\Remotion\hotelaston

Deux dossiers à connaître. Les commandes git se tapent à la racine, C:\Dev\Claude\Remotion\hotelaston (elles marchent aussi dans un sous-dossier). Les commandes npm se tapent dans C:\Dev\Claude\Remotion\hotelaston\Backend. On passe de l'un à l'autre avec cd Backend (descendre) et cd .. (remonter).

Coller dans PowerShell : clic droit dans la fenêtre, ou Ctrl + V. Rappeler une commande déjà tapée : flèche ↑.

2. Lancer et arrêter le serveur

Lancer

  1. Ouvrir PowerShell dans le projet (étape 1), puis :
    PowerShell
    cd Backend
npm start
  2. Attendre quelques secondes : des lignes s'affichent, dont l'adresse du serveur (port 3020). Le serveur tourne tant que la fenêtre reste ouverte. Ne pas la fermer ; on peut la réduire.
  3. Ouvrir le navigateur sur http://127.0.0.1:3020/admin/ et se connecter avec le compte michel@localhost. Le mot de passe est noté dans le fichier Backend\.dev-credentials (il n'est pas sur GitHub).
AdresseCe qu'on y trouve
http://127.0.0.1:3020/admin/Le back-office (l'admin)
http://127.0.0.1:3020/fr/Le site publié, tel que les visiteurs le verront
http://127.0.0.1:3020/preview/fr/La prévisualisation, brouillons compris (connexion requise)

localhost et 127.0.0.1 désignent la même chose : ce PC. Consulter /fr/ en local ajoute des visites aux statistiques de développement ; ces chiffres ne comptent pas.

Arrêter

Cliquer dans la fenêtre du serveur et appuyer sur Ctrl + C. Si Windows demande « Terminer le programme de commandes (O/N) ? », taper O puis Entrée. Fermer la fenêtre arrête aussi le serveur.

Relancer

Ctrl + C, puis ↑ pour retrouver npm start, puis Entrée. Il faut relancer après un git pull ou après avoir modifié Backend\.env.

Le cycle d'une modification dans l'admin

Modifier un texte→enregistré dans la base→Prévisualiser→Publier→visible sur /fr/

Les boutons Prévisualiser et Publier sont en haut de l'admin. En cas d'erreur, menu de gauche SITE → Publication et versions → Restaurer remet la version précédente. Le reste de l'admin est expliqué dans le manuel : menu AIDE → Manuel d'utilisation.

3. Voir le site sur le téléphone (même Wi-Fi)

C'est déjà réglé sur foupax2 : le fichier Backend\.env contient la ligne HOST=0.0.0.0. Il suffit donc :

  1. de lancer le serveur sur le PC (étape 2) ;
  2. de brancher le téléphone sur le même Wi-Fi que le PC ;
  3. d'ouvrir sur le téléphone http://192.168.1.5:3020/fr/ (l'admin : http://192.168.1.5:3020/admin/).

Si la page ne s'ouvre pas sur le téléphone :

  • L'adresse du PC a changé (la box peut en attribuer une autre). Sur le PC, taper ipconfig dans PowerShell et lire la ligne Adresse IPv4 de la carte Wi-Fi (par exemple 192.168.1.12), puis ouvrir http://192.168.1.12:3020/fr/.
  • Le pare-feu Windows bloque. Au premier lancement, Windows demande s'il faut autoriser « Node.js » : cocher Réseaux privés et valider. Si on a refusé : Démarrer → taper « Autoriser une application via le Pare-feu Windows » → Modifier les paramètres → cocher Privé en face de « Node.js JavaScript Runtime ».
  • Le Wi-Fi du PC est déclaré « Public » : Paramètres → Réseau et Internet → Wi-Fi → le réseau → Réseau privé.

Avec HOST=0.0.0.0, l'admin est joignable par tous les appareils du réseau : à garder pour la maison, pas pour un Wi-Fi public. Pour revenir en arrière, mettre HOST=127.0.0.1 et relancer.

4. Récupérer une mise à jour du code

Quand une pull request a été fusionnée sur GitHub (par exemple une modification faite par Claude), elle n'est pas encore sur le PC. Il faut la « tirer » :

  1. Dans la fenêtre du serveur : Ctrl + C pour l'arrêter.
  2. Remonter à la racine du projet et récupérer le code :
    PowerShell, dans Backend
    cd ..
git switch main
git pull

    git pull affiche la liste des fichiers changés. « Already up to date » veut dire qu'il n'y avait rien de nouveau.

  3. Seulement si la liste contient Backend/package.json ou Backend/package-lock.json (nouvelles bibliothèques) :
    PowerShell
    cd Backend
npm install
cd ..
  4. Relancer le serveur :
    PowerShell
    cd Backend
npm start
  5. Ouvrir l'admin et cliquer sur Publier : le site publié est régénéré avec le nouveau code. Certaines mises à jour ajoutent des textes ou des langues au démarrage ; ils apparaissent alors dans l'admin.

En résumé : arrêter, git pull, (npm install si besoin), npm start, Publier.

5. Comprendre GitHub en cinq mots

MotCe que c'est
Dépôt (repository)Le projet sur GitHub : github.com/mlsks/hotelaston. Le dossier du PC en est une copie.
mainLa branche principale : la version de référence du code. C'est elle que Render déploie et que le PC récupère avec git pull.
BrancheUne copie de travail à côté de main, pour essayer une modification sans toucher à la version de référence. Claude travaille toujours sur une branche (nommée claude/…).
CommitUn enregistrement des fichiers modifiés, avec un message qui dit ce qui a changé. Une branche est une suite de commits.
Pull request (PR)Une demande de verser une branche dans main. On y voit la description et chaque ligne modifiée ; on la fusionne (merge) quand elle est bonne, ou on la ferme.

La règle du projet : toute modification passe par une branche et une pull request, et n'arrive sur main que quand Michel la valide en la fusionnant.

6. Relire et fusionner une pull request

Quand Claude a terminé un travail, il donne un lien du type github.com/mlsks/hotelaston/pull/45. On peut aussi les retrouver toutes sur github.com/mlsks/hotelaston/pulls (connexion à GitHub nécessaire).

  1. Ouvrir la PR. L'onglet Conversation montre le titre et la description : ce qui a été fait, et souvent ce qu'il faut faire après la fusion.
  2. Regarder les changements (facultatif). Onglet Files changed : chaque fichier modifié, lignes retirées en rouge (-), lignes ajoutées en vert (+).
  3. Essayer avant de fusionner (facultatif, utile pour un changement visible). Sur le PC, serveur arrêté :
    PowerShell, à la racine du projet
    git fetch
git switch claude/nom-de-la-branche
# relancer (cd Backend, npm start), Prévisualiser, regarder
git switch main

    Le nom exact de la branche est écrit en haut de la PR, après « wants to merge … from ». Revenir sur main ensuite.

  4. Fusionner. En bas de l'onglet Conversation : bouton vert Merge pull request, puis Confirm merge. La pastille passe au violet « Merged ».
  5. Supprimer la branche (facultatif) : bouton Delete branch qui apparaît après la fusion. Le travail reste dans main.
  6. Récupérer la fusion sur le PC : section 4 (arrêter, git pull, relancer, Publier), et si besoin mettre à jour la démo Render.

Si la PR ne convient pas : ne pas fusionner, et le dire à Claude dans le fil du projet ; il pousse une correction sur la même branche et la PR se met à jour toute seule. Pour l'abandonner : bouton Close pull request en bas de la page (rien ne change sur main).

Si GitHub affiche « This branch has conflicts that must be resolved », ne pas résoudre soi-même : demander à Claude de mettre la branche à jour.

7. Mettre à jour la démo Render

La démo en ligne sur Render se construit à partir de la branche main de GitHub. Elle a sa propre base : ce qu'on modifie dans l'admin du PC n'y arrive pas, et inversement. Après une fusion sur main :

  1. Ouvrir dashboard.render.com, se connecter, cliquer sur le service du site.
  2. En haut à droite : Manual Deploy → Deploy latest commit.
  3. Attendre la fin (quelques minutes) : l'onglet Events affiche « Deploy live » ; l'onglet Logs montre le détail en cas d'échec.
  4. Ouvrir l'admin de la démo (l'adresse de la démo suivie de /admin/), se connecter et cliquer sur Publier.

Sur la démo, envoyer une vidéo échoue (pas de ffmpeg chez Render) ; les vidéos déjà présentes s'affichent. La démo est marquée « ne pas indexer » (NOINDEX=1) : Google ne la référence pas.

8. Faire et pousser ses propres modifications

Pour changer soi-même un fichier du code ou de la documentation (pas les textes du site, qui se changent dans l'admin), on suit le même chemin que Claude : branche, commit, push, pull request.

Une seule fois : se présenter à Git

Git signe chaque commit avec un nom et un e-mail. À faire une fois sur le PC (remplacer par ses propres valeurs ; l'e-mail est celui du compte GitHub) :

PowerShell
git config --global user.name "Michel"
git config --global user.email "votre-adresse@exemple.com"

Au premier git push, une fenêtre GitHub s'ouvre pour se connecter (bouton Sign in with your browser, puis Authorize). Windows retient ensuite la connexion.

Les étapes

  1. Partir d'un main à jour, à la racine du projet :
    PowerShell
    git switch main
git pull
  2. Créer une branche avec un nom court, sans espace ni accent :
    PowerShell
    git switch -c michel/correction-guide
  3. Modifier les fichiers (Bloc-notes, VS Code…), enregistrer.
  4. Vérifier ce qui a changé :
    PowerShell
    git status
git diff

    git status liste les fichiers modifiés (en rouge). git diff montre les lignes ; taper q pour en sortir. Vérifier qu'aucun fichier inattendu n'apparaît (.env, base, photos : ils sont normalement ignorés).

  5. Enregistrer un commit :
    PowerShell
    git add -A
git commit -m "Guide : précise l'étape du pare-feu"

    Le message dit en une phrase ce qui change. On peut faire plusieurs commits sur la même branche.

  6. Pousser la branche sur GitHub :
    PowerShell
    git push -u origin michel/correction-guide

    Les fois suivantes, sur la même branche, git push suffit.

  7. Ouvrir la pull request. Aller sur github.com/mlsks/hotelaston : un bandeau jaune propose Compare & pull request. Cliquer, vérifier que la flèche va bien de michel/correction-guide vers main, écrire un titre et une description, puis Create pull request. (Sans bandeau : onglet Pull requests → New pull request → choisir la branche dans « compare ».)
  8. Fusionner comme en section 6, puis revenir sur main sur le PC :
    PowerShell
    git switch main
git pull

Cas particulier, le guide de l'admin. Ne modifier que docs\guide-utilisateur.md, puis régénérer sa version HTML avant le commit (un test vérifie qu'elle est à jour) :

PowerShell, à la racine du projet
node tools/md-to-html.mjs docs/guide-utilisateur.md

Après une modification du code, lancer aussi les tests : npm test dans Backend (tous doivent réussir ; un test est sauté sans ffmpeg).

9. Ce qui est sur GitHub, et ce qui ne l'est pas

ÉlémentOù il vitComment il bouge
Code du back-office, gabarits, maquette, documentationGitHub + dossier du PCgit pull, git push, pull requests
Textes, traductions, fiches, réglages, comptes, versions publiéesBackend\storage\ (base SQLite) sur le PCAdmin → Publier. Jamais par git.
Photos, vidéos, sons de la médiathèqueBackend\media\ sur le PCAdmin → Médiathèque. Jamais par git.
Réglages locaux (port, HOST…)Backend\.env sur le PCBloc-notes, puis relancer le serveur
Mots de passe de développementBackend\.dev-credentials sur le PCNe jamais le copier ni l'envoyer

Sauvegarde. Comme la base et les photos ne sont pas sur GitHub, copier régulièrement Backend\storage et Backend\media sur un disque externe ou un cloud, serveur arrêté de préférence.

10. Problèmes fréquents

Au lancement du serveur

Message ou symptômeQue faire
npm.ps1 cannot be loaded because running scripts is disabledUne fois : Set-ExecutionPolicy -Scope CurrentUser RemoteSigned, répondre O. Ou taper npm.cmd start au lieu de npm start.
npm, node ou git « n'est pas reconnu »Fermer et rouvrir PowerShell. Si ça persiste, le logiciel n'est pas installé : voir docs\INSTALLATION-LOCALE.md.
Missing script: "start" ou ENOENT … package.jsonOn n'est pas dans le bon dossier : cd C:\Dev\Claude\Remotion\hotelaston\Backend.
EADDRINUSE … 3020Un serveur tourne déjà (une autre fenêtre npm start, parfois réduite). L'arrêter ou l'utiliser. Sinon, redémarrer le PC.
Cannot find module … après un git pullNouvelles bibliothèques : npm install dans Backend, puis npm start.
EBUSY ou EPERM à la publicationUn programme tient un fichier : fermer les autres serveurs, un explorateur SQLite, attendre l'antivirus, puis recommencer.
Le navigateur affiche « Impossible d'accéder au site »Le serveur n'est pas lancé, ou la fenêtre affiche une erreur : la lire, relancer npm start.

Sur le site et l'admin

SymptômeQue faire
Ma modification n'apparaît pas sur /fr/Elle est enregistrée mais pas publiée : Publier. Puis recharger la page sans cache : Ctrl + F5.
Une mise à jour de Claude n'apparaît pasLa PR est-elle fusionnée (pastille violette) ? Puis git pull, relancer, Publier.
/fr/ est vide ou en 404Rien n'est publié : Publier dans l'admin.
Une publication a cassé quelque choseSITE → Publication et versions → Restaurer la version précédente.
Le téléphone n'ouvre pas le siteVoir section 3 : adresse IPv4, pare-feu, réseau privé.

Avec Git et GitHub

MessageCe que ça veut dire, et que faire
fatal: not a git repositoryOn n'est pas dans le projet : cd C:\Dev\Claude\Remotion\hotelaston.
Your local changes to the following files would be overwritten by merge (au git pull)Un fichier du code a été modifié sur le PC. Pour mettre ces changements de côté puis récupérer la mise à jour : git stash, git pull. Pour les jeter définitivement à la place : git restore nom-du-fichier. En cas de doute, demander à Claude avant.
Une fenêtre étrange s'ouvre dans le terminal avec « Merge branch… » (éditeur Vim)Git demande un message de fusion. Taper :wq puis Entrée pour accepter le message proposé.

Please tell me who you areFaire l'étape « Se présenter à Git » de la section 8.
Permission denied ou Authentication failedReconnexion à GitHub : relancer git push et suivre la fenêtre de connexion. Si elle ne s'ouvre pas : Démarrer → « Gestionnaire d'identification » → Informations d'identification Windows → supprimer l'entrée git:https://github.com, puis réessayer.
Je ne sais plus sur quelle branche je suisgit status : la première ligne dit « On branch … ». Revenir à la référence : git switch main.
git switch refuse : « Your local changes … would be overwritten by checkout »Des modifications ne sont pas commitées. Les enregistrer (git add -A, git commit -m "…") ou les mettre de côté (git stash) avant de changer de branche.
